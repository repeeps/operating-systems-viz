PART C · 메모리의 마법 — CH 11

번역을 빠르게 — TLB

CH10에서 모든 메모리 접근은 페이지 테이블 조회를 거친다고 했죠. 그런데 그 표는 메모리에 있어요 — 즉 데이터 한 번 읽으려면 표 보러 메모리 또 한 번. 번역 때문에 접근이 두 배로 느려지는 셈이에요. 해법은 최근 번역 결과를 곁에 작게 캐싱하는 것 — 그게 TLB예요. 프로그램은 같은 페이지를 연달아 쓰는 경향(지역성)이 강해서, 대부분의 접근이 TLB에서 즉시 해결돼요.

Step 00 — The Table Is Far

번역하느라 메모리를 두 번

데이터를 한 번 읽으려면: ① 페이지 테이블(메모리에 있음)을 봐서 프레임을 알아내고, ② 그 프레임의 데이터를 읽어요. 메모리 접근이 두 번이 되는 거죠. 메모리는 CPU 기준으로 꽤 느린 편이라, 매번 두 번씩이면 프로그램 전체가 눈에 띄게 굼떠져요. 뭔가 손을 써야 해요.

→ 번역(표 조회)+데이터 = 메모리 2회. 매 접근마다라면 너무 느려요.

Step 01 — A Cache Beside the CPU

최근 번역을 곁에 두기

TLB는 CPU 바로 옆에 있는 아주 작고 빠른 표예요. 최근에 번역한 "페이지→프레임" 몇 개만 들고 있죠. 메모리 접근 때 먼저 TLB를 보고, 거기 있으면(적중) 느린 페이지 테이블을 건너뛰고 즉시 프레임을 알아내요. 없으면(빗나감) 그때만 메모리의 표를 보고, 그 결과를 TLB에 적어 둬 다음을 대비해요.

→ TLB = CPU 곁의 작은 번역 캐시. 적중하면 느린 표를 건너뜀.

Step 02 — Hit and Miss

왜 대부분 적중할까

TLB는 작은데 어떻게 대부분의 접근을 해결할까요? 프로그램은 방금 쓴 곳 근처를 곧 또 쓰는 경향이 강하거든요(반복문·배열 순회 — 지역성). 그래서 같은 몇 페이지가 연달아 쓰여 작은 TLB로도 적중률이 높아요. 접근 패턴을 토글로 바꿔 적중률이 어떻게 달라지는지 보세요 — 한곳에 모이면 잘 맞고, 마구 흩어지면 자주 빗나가요.

→ 지역성이 높을수록 적중률↑. 고정된 99% 같은 숫자가 아니라, 접근 패턴이 좌우해요.

Step 03 — Takeaways

정리

TLB는 최근 번역을 CPU 곁에 캐싱해, 번역이 데이터 접근을 두 배로 느리게 만드는 문제를 거의 없애요. 작아도 잘 듣는 이유는 지역성 — 프로그램이 같은 페이지를 몰아 쓰기 때문이죠. 이건 책 전체에 흐르는 캐싱이라는 큰 패턴의 한 사례예요(자주 쓰는 걸 가깝게 둔다). 여기까진 "필요한 페이지가 물리 메모리에 이미 있다"고 가정했어요. 그런데 그 페이지가 아직 메모리에 없다면? 다음 챕터.
